# 会议音频桥接

将正式会议称为 A、同事通话称为 B。默认 A=腾讯会议，B=钉钉；用户指定其他软件时，先核实其独立输入/输出选择能力。此 skill 编排现有音频设备和客户端，不实现虚拟声卡或网络传输。

## 先明确模式

- **旁听 listen**：A 的声音送给 B，A 使用本机麦克风。B 听不到本机说话；不能将它描述为完整三方通话。
- **双向 two-way**：在旁听基础上，B 的声音可送入 A。A 麦克风在实体麦克风（本机发言）与返程 BlackHole（同事发言）之间切换。用这一路径满足普通双向请求。
- **混音 mix**：本机与同事同时发言，且两边都能听到本机。读取 [混音模式配置](references/simultaneous.md)，选定配套原生原型（native）、LadioCast 或 Loopback，生成两份排除接收方原声的混音。生成器只规划路由，实际混音由选定软件执行；聚集设备不能代替混音器。

用户已说明模式、平台或设备时不重复询问。模式未给出时生成双向方案，配置后保持 A 静音、本机麦克风待机。实施桥接不包括自动加入、邀请、录音、发消息或替用户在正式会议解除静音；这些行为只按实际授权执行。设置变更已有授权时直接继续。

原生混音已具备配套项目时，读取 [CLI 操作](references/cli.md)，优先使用 JSON 命令完成发现、校验、运行、状态查询和停止；GUI 与 CLI 共用音频引擎。Python 计划生成器不是运行时控制程序。

## 检查与生成方案

1. 用下列只读脚本检查设备；`<skill-dir>` 为本文件所在目录，不依赖工作目录：

   ```sh
   python3 <skill-dir>/scripts/bridge.py doctor
   ```

   空设备列表或失败表示当前进程无法确认，使用「音频 MIDI 设置」界面核实。`observed` 只表示看见设备，不能作为已连通证据。脚本不读取会议内容、不安装驱动。
2. 读取 [Mac 配置与排障](references/macos.md)。确认实体耳机和麦克风的实际名称，以及 BlackHole 2ch / 16ch 是否可用。需要安装驱动时按现有授权安装；不得仅因用户要求“写一个 skill”就在其机器安装驱动。
3. 生成方案（替换实际设备名）：

   ```sh
   python3 <skill-dir>/scripts/bridge.py plan --mode two-way --headphones '实际耳机名称' --microphone '实际麦克风名称' --output /absolute/session-dir/plan.json
   ```

   方案是期望状态，不证明设备存在；命令不更改系统。`listen` 只需要 2ch；`mix` 使用 `--mixer` 及混音参考里的命令。设备名称必须匹配实际 UI；同名设备通过 UID/界面上下文区分，不能按列表顺序猜。改名的驱动可通过 `--forward` / `--return-bus` 指定，但名称相异不证明通路独立。

## 配置与恢复记录

在变更前，将以下实际值记入工作目录下的会话记录（不要放进 skill 仓库或提交到 Git）：A/B 的应用名与版本、输入、输出、静音状态；系统默认输入/输出；已有多输出设备的名称、成员、采样率、主时钟、漂移修正；本次创建的设备及变更。未知项写 `unknown`，不得伪造可恢复快照。

优先使用可用的原生应用界面工具查看「音频 MIDI 设置」和两款客户端。先读取工具文档和当前控件，再操作；不使用猜测坐标、私有配置文件键或未经验证的 AppleScript。没有 UI 工具时给出具体步骤，标为等待手动配置；不将“已生成方案”报告成“已配置”。

按 plan.json 的 `multi_outputs` 建设备，`settings` 配置软件。先使 A 静音，再改路由；完成保持其静音，待测试或用户发言指令。只改选定客户端的输出，通常无需将整个系统声音转发。已有同名多输出设备先核实成员，勿覆盖不相关设备。音频声道与时钟细节见 macos.md。

`mix` 先读取所选后端的配置步骤。原生后端用两张混音声卡，客户端扬声器改为实体耳机；外部后端用四条通路并保留原声多输出。先静音两边，按 `mixer.outputs` 配置并检查实际混音，再执行 `operations.enable_mix` 切换客户端输入。原生后端还需确认实际音频进程和系统权限。若混音器或独立输出设备不足，保留当前模式并报告混音尚未启用；不要提前将客户端接到空的混音设备。

## 必须保持的音频关系

- 切换模式：A 输出 → 正程 BlackHole → B 输入；B 输出 → 返程 BlackHole → A 输入。混音模式在两路原声之后分别加入本机麦克风，再送到对应客户端输入；原生后端的原声来自应用 Tap。
- 正程和返程使用不同的独立设备；标准配置是 2ch 与 16ch，分别用声道 1–2。
- 耳机只接收，不回送。两端戴耳机；不要启用将输入再次送回同一总线的监听。
- A 输出不可进入 A 输入，B 输出不可进入 B 输入。BlackHole 的镜像设备不等于独立总线。
- “多输出设备”复制输出；“聚集设备”并列声道；两者都不会自动把实体麦克风与同事声音相加。

## 发言操作

按生成方案的 `operations` 执行设备切换；每次先静音 A，再切换其麦克风。用户要求实际发言时才将最后一步解除静音作为此次操作的一部分。以下本机/同事切换步骤适用于 `listen` / `two-way`；`mix` 的同时发言、内部讨论和退出使用 [混音模式操作](references/simultaneous.md)。

- **本机发言**：A 输入设实体麦克风。B 仍只听得到 A 的远端声音，听不到本机语音。
- **同事发言**：A 输入设返程 BlackHole；B 输入保留正程且须解除静音。此时 A 解除静音会广播 B 的声音。
- **内部讨论**：保持 A 静音，将 B 输入临时设实体麦克风；使用耳机听 B。此时 B 暂停旁听 A。恢复桥接时先在 A 静音状态恢复 B 输入=正程，再选 A 的发言人输入。
- **恢复**：先静音两边，将 A/B 输入输出恢复到会前实际值，再恢复确实改过的系统设置。只删除本次新建且不再使用的多输出设备，不卸载 BlackHole、不重启 CoreAudio。恢复原“未静音”状态前考虑当前是否仍在正式会议，不自动开放麦克风。

## 验证与交付

读取 [会前验证](references/verification.md)，用独立的远端参与者验证 A→B 和 B→A。用户未授权测试通话时完成设备检查并列出待测项目，不自行联系同事。电平跳动不等于远端听到了，也不能证明无回声。

交付当前模式、实际设备表、哪些设置已完成、哪些传输经过远端确认、待测项与恢复记录位置。只有配置观察通过且真实两端测试通过，才说“已验证可双向通话”。保留客户端版本和测试日期，后续更换耳机或更新客户端需重测受影响路径。
